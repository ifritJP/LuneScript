# LuneScript を使ってみた感想

wasm (WasmGC) への直接変換 (`wasm_direct_design.md`) の作業で、LuneScript を書き、コンパイラを読み、
Lua 版・go 版の lnsc で変換・実行してきた。その中で感じたことを、いくつかの観点でまとめる。

- 書いた人: Claude (Anthropic の AI アシスタント)。LuneScript の作者とやり取りしながら作業した
- 書いた時点: 2026-10-17 (`support_direct_wasm` の `6656e8f3` の時点)
- 作業の範囲: `convWasm.lns` / `WasmRt.lns` / `WasmBin.lns` (合わせて約 6,400 行) の作成、
  コンパイラ・ランタイム・フォーマッタの既存の不具合の修正、ベンチマーク (`wasm_benchmark.md`)

## 1. ソフトウェアエンジニアとして

### 良いと感じた点

- **nil を型で扱えるのが心強い。**
  `int!` のような nilable 型と、`let!` / `if!` / `when!` / `unwrap!` の組み合わせで、
  nil の確認漏れをコンパイル時に防げる。6,400 行の変換器を書いても、nil の参照による実行時エラーはほとんど無かった。
- **alge と `match` が書きやすい。**
  wasm の命令の木 (`Ins`) や変数の置き場所 (`VarLoc`) をパラメータ付きの alge で表せた。
  `match` で全ての値を扱っていないとエラーになるので、場合分けの漏れが無い。
- **mutable / immutable の区別が厳密。**
  `&` (immutable な参照) と `mut` の区別で、共有している List を誤って書き換える心配が少ない。
- **型推論が効くので、静的型付けの割に記述量が少ない。**
  局所変数の型はほぼ書かずに済んだ。
- **テストの仕組みが強い。**
  `make -j1 test-comp-with-go` は、コンパイラ自身を 2 世代変換して出力が一致すること (不動点) と、
  Lua 版・go 版のテスト結果の一致を確認する。変換器を大きく変えても、壊していないことを確信できた。

### 戸惑った点

- **`continue` が無い。** ループの途中で次の繰り返しに進む処理を、`if` の入れ子や `elseif` の連鎖で書く必要があった。
- **構文の組み合わせの制限が多く、エラーメッセージから原因がわかりにくい。**
  - `if! ... elseif` は書けず、エラーは `illegal exp` だけだった。
  - `when!` は局所変数と引数にしか使えない (`node.$left` には使えない)。
  - Map に `#` を使えない (`unmatch type for "#"`)。
  - `_switch` は str に使えず、`_match` に `default` を書けない。
  - `local`・`global` は予約語で、変数名に使えない。
- **mutable の規則が、慣れるまで直感に反する。**
  `let rect = new Rect(...)` は immutable な参照になるので、`List<Shape>` に `insert` できない。
  エラーは `type mismatch @Shape <- &Rect ... use the option '--legacy-mutable-control'` で、
  原因が `let mut` を付け忘れたことだとすぐにはわからなかった。
- **関数型の書き方が統一されていない。**
  引数・戻り値に `fn( int ) : int` とは書けず、`form IntFn( x:int ) : int;` と宣言する必要がある。
  `form` の値は `f( ## )` で呼べるが、引数の無い `form` を宣言した型の値を `f( ## )` で呼ぶと `over exp` のエラーになる。
- **`default_async_all` のクロージャの制限。**
  非同期の扱いのため、クロージャから mutable な局所変数を参照できない
  (`can't access the mutable type's symbol ... from async`)。簡単な補助のクロージャを書けない場面があった。
- **`-Werror` の警告が多い。**
  多値を返す関数の呼び出しに `**` を付ける、`##` を使う、などの警告は意図を明示させる良い仕組みだが、
  コンパイラ自身のビルドでは `-Werror` なので、書き始めのうちは警告の対応に時間を取られた。
- **ビルドが重い。**
  `make -j1 test-comp-with-go` は数分かかる。コンパイラの意味を変える修正や、
  古いコンパイラが扱えないテストを追加する場合は、2 段階 (先にコンパイラを accept し、次にテストを足す) で進める必要がある。

## 2. altLua 言語として

### 良いと感じた点

- **Lua の意味をそのまま保っている。**
  int と real の区別、`==` での int と real の同一視、床除算、Lua のパターン、`string.format` の書式など、
  Lua 5.3 の動作に合わせてある。Lua のライブラリ・資産をそのまま使える。
- **Lua の弱い部分を補っている。**
  静的型、nilable、クラス・インタフェース・generics、alge、Mapping、マクロがあり、大きなプログラムを Lua の上で書ける。
  Lua のコードを直接扱う `Luaval` や `_load` もある。
- **Lua 5.1〜5.4 に対応している。** テストでもバージョンの差を印 (`/*nolua51*/`) で管理している。

### 気になった点

- **出力した Lua が、宣言の順番に依存していた。**
  後で定義するローカル関数を参照するコードは、コンパイルは通るが、Lua に変換すると実行時に
  `attempt to call a nil value` になった (`dev_with_llm` で修正済み)。コンパイラ自身でも 12 モジュール・60 関数が該当しており、
  呼び出しの順番の都合でたまたま動いていた。
- **実行時エラーが Lua のエラーとして出る。**
  `string.format` の書式の誤りなどは、Lua のスタックトレースとして表示される。
  LuneScript のソースの位置に対応付けにくい。

## 3. altGo 言語として

### 良いと感じた点

- **ネイティブの速度が出る。**
  ベンチマーク (`wasm_benchmark.md`) では、整数演算・クラス・コレクションなどで、wasm 版より速い。
  実行ファイルも小さい (ベンチマークで約 2.5MB)。
- **同じソースから Lua 版と go 版を作れる。**
  `test/testGo.lns` で両者の出力を比べる仕組みがあり、変換の誤りを見つけやすい。

### 気になった点

- **Lua の意味と go の意味の違いから来る不具合が残っていた。** 今回見つけて修正したもの:
  - `string.format( "%c" )` が 128 以上の値を UTF-8 の 2 バイトで出力していた (go の `%c` は rune)。
  - 2^53 を超える整数リテラルが不正確になっていた (`tonumber()` が float64 を経由する)。
  - シフトの意味 (Lua は論理シフトで、シフト量が 64 以上なら 0)。
  - ビット演算の優先順位 (`x + y & 1` が go では `x + (y & 1)` になっていた)。
  - 引数の無いクロージャを `form` に変換すると、go のコンパイルが通らなかった。
  どれも Lua 版では正しく動き、go 版でだけ結果が変わる (またはビルドできない) 種類の不具合で、
  go 版のテストの網羅を広げる価値があると感じた。
- **生成した go のコードを単体でビルドする手順が重い。**
  生成したコードは `github.com/ifritJP/LuneScript/src` の `runtime_go` を import するので、
  そのモジュール名の `go.mod` を用意し、ランタイムのソースをコピーする必要がある
  (ベンチマークでは `src/go.mod` をコピーして対応した)。Lua を使う場合は cgo と `lua-5.3.pc` も必要になる。
- **go 版の lnsc で、実行中の Lua のエラーが異常終了になる。**
  `lnsc ... exe` で Lua のエラーが起きると、`PANIC: unprotected error` と全 goroutine のダンプを出して終了する
  (Lua 版の lnsc は通常のエラーとして表示する。未修正)。
- **値の表現が go らしくない部分がある。**
  nilable の値や generics は `LnsAny` (interface) で表し、全ての関数が `_env` を受け取る。
  Lua と同じ意味を保つための代償で、go のライブラリから呼ぶ場合には使いにくい。

## 4. トランスコンパイラとして

### 良いと感じた点

- **新しい出力先を追加しやすい構造。**
  AST を `Nodes.Filter` でたどる構造で、Lua・go・python の変換器が並んでいるので、
  wasm の変換器 (`convWasm.lns`) も同じ形で追加できた。`-langWasm` のオプションの追加も小さな変更で済んだ。
- **AST に、出力に必要な情報が揃っている。**
  クロージャが参照する変数 (`$closureSymList`、`$hasAccessFromClosure`)、多値の位置 (`$mRetExp`)、
  暗黙の cast (`ExpCastNode` の `castKind`)、型情報 (`TypeInfo`) など、
  変換器の側で解析をやり直さずに済んだ。
- **セルフホストしている。**
  変換器そのものを LuneScript で書けるので、作った変換器を LuneScript のコンパイラ自身で試せる。
  wasm 版の最終目標 (lnsc を wasm にして自分自身をコンパイルする) も、この性質があるから現実的になる。

### 戸惑った点

- **AST の細部が、読まないとわからない。**
  - 暗黙の cast (`ExpCastNode` の `Implicit`) の `expType` は、cast 後ではなく cast 前の型になっている (`castType` が cast 後の型)。
  - `a, b = f();` では、同じ多値の式 (`ExpMRetNode`) を、値ごとに別の `ExpCastNode` で包んでいる。
  - str の型 (`builtinTypeString`) の種類が `TypeInfoKind.Class` になっている。
  - builtin のメソッドの getter の `$rawTxt` が `<head>` になっている。
  `Nodes.lns` にはコメントがあるが、変換器を書く側から見た「AST の読み方」の資料があると、新しい出力先を作る人の助けになる。
- **言語の意味が Lua で決まっていることの重さ。**
  床除算・論理シフト・int と real の同一視・Lua のパターンなどを、Lua 以外の出力先でも再現する必要がある。
  wasm では `%` や `/` が補助の関数の呼び出しになり、ベンチマークで遅くなる原因の一つになった
  (定数で割る場合などは変換時に最適化できる)。go 版でも `Lns_shiftL` などのランタイムの関数を使っている。
  Lua 互換を保つ設計上の選択なので、出力先ごとの最適化で補うのが良いと考える。
- **出力先の間の差を見つける仕組みが、出力先ごとにある。**
  Lua 版と go 版の比較 (`test-go`) と、Lua 版と wasm 版の比較 (`test-wasm`) が別々にある。
  同じテストを全ての出力先で実行し、Lua 版と比べる共通の仕組みにすると、今回のような go 版だけの不具合を見つけやすくなる。

## 5. まとめ

LuneScript は、Lua の上で静的型・nil 安全・alge などを使えるようにした、実用的な言語だと感じた。
特に nilable 型と alge・`match` は、大きな変換器を書くときに確実に効いた。
一方で、構文の組み合わせの制限と、それを伝えるエラーメッセージには改善の余地がある。

トランスコンパイラとしては、AST の情報が豊富で、新しい出力先を追加しやすい。
言語の意味を Lua に合わせていることは、Lua の資産を使える強みであると同時に、Lua 以外の出力先での速度と正しさの課題にもなる。
今回 go 版で見つかった不具合はその典型で、出力先をまたいだ比較テストの充実が効果的だと考える。
