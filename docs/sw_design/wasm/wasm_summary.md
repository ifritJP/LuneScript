# wasm 対応のまとめ

LuneScript のコードを Go を経由せずに wasm (WasmGC) へ直接変換する対応 (`support_direct_wasm` ブランチ) を振り返る。
設計と実施内容の詳細は [wasm_direct_design.md](wasm_direct_design.md)、性能は [wasm_benchmark.md](wasm_benchmark.md)、
残っている課題は [wasm_issue.md](wasm_issue.md) を参照。

- 書いた人: Claude (Anthropic の AI アシスタント)。LuneScript の作者の指示とレビューを受けながら、設計・実装・テスト・文書化を行った
- 書いた時点: 2026-10-20 (`889658fd` + 未コミットの変更 (WASI 対応・Lua 版 lnsc の埋め込み))

- wasm 版の lnsc は、lnsc の全モジュールの変換で 1 コアの Go 版の 1.1 倍、lnsc 自身の wasm への変換では 1 コアの Go 版より速い。Lua 版の約 6 倍速い。
- 小さなベンチマークでは、インスタンスを多く生成する処理と文字列の処理は Go 版より速く、計算が主の処理は Go 版の 1.5〜2.4 倍かかる。

### 2.3 作業中に見つけて直した既存の不具合

wasm の変換結果を Lua 版と比べる過程で、既存のコンパイラ・ランタイムの不具合が見つかった
([wasm_direct_design.md](wasm_direct_design.md) の 14.3 など)。

- Go 版ランタイムの `string.format( "%c" )` が 128 以上の値を UTF-8 で出力していた
- Go 版 lnsc で、2^53 を超える整数リテラルが不正確になる
- `while` の条件に `and` を使うと、ループの後の文が「到達しない」と誤判定される
- 後で定義する関数を参照するコードを Lua に変換すると、実行時に `nil` の呼び出しになる (lnsc 自身の 12 モジュール・60 関数が該当)
- 右シフトが Lua では論理シフト、Go では算術シフトになる。Go への変換で `~` (排他的論理和) が `^` にならない
- マクロの中の `__line__` の値、`make -j` での `test-comp` の間欠的な失敗
- Go 版 lnsc の並列の解析で、クロージャが捕捉する変数の情報が揃わない (wasm では並列にしないことで回避。未修正)

## 4. 別の言語 (変換先) に対応する場合のアドバイス

wasm 対応の経験から、LuneScript に新しい変換先を追加する場合の進め方と注意点をまとめる。

### 4.1 進め方

1. **Lua 版を正解 (オラクル) にした差分テストを最初に作る。**
   同じ `.lns` を Lua 版で `exe` した結果と、新しい変換先で実行した結果を `diff` する (`make test-wasm` の形)。
   既存の `test/tutorial`・`test/testGo.lns`・`test/start.lns` がそのまま使えるので、テストを新たに書く量は少ない。
   未対応の部分は、行番号を保ったまま空行にする印 (`skip-wasm`・`// nowasm`) で除き、印を減らしていく形で進捗を管理できる。
2. **小さいテストから順に広げる。**
   M0 (式・制御文) → tutorial → `testGo.lns` → `start.lns` → Lua 連携 → セルフホスト、の順。
   各段階で全テストの差分が 0 になってから次に進むと、後の段階で原因の切り分けに困らない。
3. **最後にセルフホストの不動点を確認する。**
   新しい変換先の lnsc で lnsc 自身を変換し、同じ出力になること (不動点) と、全モジュールの変換結果が Lua 版と一致することを確認する。
   約 74,000 行のコンパイラが動くので、言語機能の網羅的なテストになる。wasm ではここで変換器の不具合が 4 件見つかった。
4. **性能はプロファイラで確認してから直す。**
   wasm では、Lua のランタイムを呼ぶ部分 (文字列のコピー) が全体の 57% を占めていて、推測していた原因 (コード生成) とは違った。

### 4.2 Lua と意味を合わせる必要がある点

LuneScript の意味は Lua の動作に強く依存している。新しい変換先で特に注意が必要だった点:

| 点 | 内容 |
|---|---|
| 整数の演算 | `//`・`%` は床除算 (負の数で C 系と異なる)。シフトは論理シフトで、シフト量が 64 以上・負の場合も Lua と同じにする |
| 実数の文字列化 | `%.14g` で、整数値の実数は `1.0` になる。正確な丸めの実装は難しいので、Lua を使った |
| `string.format`・パターン (`find`・`gsub`・`gmatch`) | Lua の書式・パターンは独自なので、Lua の実装 (lstrlib) を使うのが確実。頻繁に使う単純な書式だけ自前で処理し、それ以外は Lua に任せる二段構えにする (Go 版も同じ) |
| 文字列 | バイト列。`lower`・`upper` は ASCII だけ。比較はバイト単位 |
| Map のキー | int と real の同じ値は同じキー。Map の要素の順番は決まっていないので、出力の比較には `forsort` を使うコードが多い |
| 多値・`##` | 関数の戻り値の数が可変 (省略した戻り値の数で値の数が変わる)。可変長引数 (`...`) の nil の扱い |
| ソート | Lua の `table.sort` は不安定ソート。出力に影響する場合は、安定ソートにして順番を決める (不動点の確認で問題になった) |
| マクロ | マクロは Lua のコードとして実行される。セルフホストするには、変換先で Lua を動かすか、Lua 版の lnsc を埋め込む必要がある |

### 4.3 対応しやすい変換先・難しい変換先

LuneScript の言語機能 (GC、クロージャ、nilable、generics (型消去で済む)、多値、インタフェース、alge) と、
Lua との連携 (マクロの実行・`Luaval`) を考えると:

| 変換先 | 評価 | 理由 |
|---|---|---|
| JavaScript / TypeScript | 対応しやすい | GC・クロージャ・動的な型がある。Lua も wasm (今回の `lnslua.wasm`) や JavaScript 実装で動かせる。整数が 64 ビットでない (`BigInt` が遅い) 点だけ注意が必要 |
| Java / Kotlin / C# | 対応しやすい | GC・クロージャ・インタフェース・generics (型消去で可) がある。Lua の実装 (LuaJ・NLua など) がある。多値はタプルやオブジェクトで表す |
| Python | 対応済み (`convPython.lns`) | 動的な型付けで、意味の差は数値の演算と文字列 (バイト列) が中心 |
| wasm (WasmGC) | 今回対応 | GC を言語処理系に任せられる。ただし、命令レベルでランタイム (Map・List・文字列) を書く必要があり、Lua との連携は線形メモリとの間でコピーが要る |
| C / C++ / Rust | 難しい | GC が無いので、GC (または参照カウントと循環の回収) を自前で用意する必要がある。Rust は所有権のモデルと、LuneScript の共有される mutable なオブジェクトが合わない |
| Swift | やや難しい | ARC (参照カウント) で、循環参照の回収が無い |

新しい変換先を選ぶ時の判断基準:

- GC があるか (無い場合はランタイムの規模が大きく増える)
- クロージャ (変数の捕捉) があるか。無い場合は、捕捉する変数をセルにする変換が要る (wasm はこれを自前で行った)
- Lua を組み込めるか (マクロの実行とセルフホストに必要)
- 64 ビット整数と、Lua と同じ整数の演算を効率よく書けるか

### 4.4 ランタイムの作り方

- Go 版の `runtime_go` と同じく、`limit_conv_code lua` のモジュール (`Str`・`Depend`・`DependLuaOnLns`) は、
  変換先の言語で書いたランタイムに置き換えると速い。wasm でも、`Str.Builder`・`Str.getLineList`・`Depend.getFileLastModifiedTime` を置き換えた。
- ただし、Lua 版と結果が変わらないことを優先する。Go 版の `Str.startsWith` (`HasPrefix`) は、Lua 版 (「含むかどうか」) と結果が違っていた。
- Lua を呼ぶ処理は、想定外の引数の場合に Lua に任せる形にしておくと、エラーのメッセージなども含めて Lua と同じにできる。

## 5. 所感・その他

### 5.1 LuneScript での言語処理系の開発

- **変換器を LuneScript で書くのは快適だった。** nilable の型・alge と `match`・mutable / immutable の区別のおかげで、
  10,000 行を超える変換器を書いても、nil の参照などの実行時エラーはほとんど無かった。wasm の命令の木を alge で表し、
  バイナリの出力も LuneScript の文字列 (バイト列) でそのまま書けた。詳しくは [impression.md](../impression.md) を参照。
- **フロントエンドの情報が揃っているので、変換器に集中できる。** 型付きの AST、クロージャが捕捉する変数、
  import するモジュールの AST などをフロントエンドが用意している。wasm の変換器が既存のフロントエンドに求めた変更は、
  並列の解析の問題 (2.3) を除いてほぼ無かった。
- **1 つの AST から複数の言語を出力できる構造が役立った。** Lua 版 lnsc の埋め込みでは、wasm に変換するのと同じ AST から
  Lua のコードも生成して埋め込んだ。どちらの変換器も同じプロセスで使えるので、ファイルの置き場所に依存しない。
- 戸惑った点:
  - `__init` からプロトタイプ宣言したメソッドを呼べない、局所関数から外側の mutable な変数を使うと async の制約でエラーになる
    (`default_async_all` のモジュール)、など、言語の制約に合わせてコードの形を変える場面があった。
  - `gsub` が 2 つの値を返すので、`"%s" (txt.gsub(...))` のような書式の引数では `( )` で 1 つにする必要がある。
  - Lua 版の lnsc は遅い (全モジュールの変換に約 12 秒) ので、変換器を変更するたびのセルフホストのビルドに時間がかかる。
    Go 版の lnsc (約 0.4 秒) を併用すると効率が良い。
  - LuneScript で書いた単純な文字列の連結 (`txt = txt .. item` の繰り返し) は、Lua・Go・wasm のどれでも要素数 × 全体の長さに比例する時間がかかる。
    出力が大きくなると目立つので、`string.__join` などでまとめて連結する (14.11 で 2 箇所を直した)。

### 5.2 テスト環境

- **既存のテスト資産が最大の助けになった。** `test-comp-with-go` (2 世代のセルフホストと Lua 版・Go 版の結果の比較)、
  `testGo.lns`・`start.lns` の大きなテストがあったので、Lua 版を正解とした差分テストをすぐに作れた。
  wasm の変換が Lua 版と 1 バイトでも違えば検出できたので、意味の差を見逃さずに済んだ。
- **変換先を増やすと、既存の不具合が見つかる。** 同じテストを別の実装で動かすと、Lua 版・Go 版それぞれの不具合も見つかる (2.3)。
- 改善した点: `test-comp` を `make -j` で並列に実行した時の間欠的な失敗を直し、失敗の箇所を見つけやすくした。
  wasm のテストは `make test-wasm`・`test-wasm-selfhost` と、WASI 用の `test-wasm-wasi`・`test-wasm-selfhost-wasi` にまとめた。
- 今後あると良いもの: Lua と意味が違う点 (4.2) を網羅した、変換先に依存しない比較テスト
  (`../improvement_plan.md` の「出力先をまたいだ共通の比較テスト」)。

### 5.3 WebAssembly について

- WasmGC のおかげで、GC を自前で書かずに済み、Node.js (V8) の世代別 GC の恩恵も受けられた。
  インスタンスを多く生成する処理は Go 版より速い。
- 一方、ファイナライザ・弱参照が無いので、Lua の値の参照を解放できない ([wasm_issue.md](wasm_issue.md) の 2.1)。
- V8 の wasm には実行中の関数を最適化版に切り替える仕組み (OSR) が無く、`--no-liftoff` などコンパイルの段階の調整が性能に大きく影響した。
- WASI のランタイム (wasmtime 49) は動作は正確だが、WasmGC の性能は V8 に大きく劣る (約 9〜13 倍)。
  例外処理の命令の形式 (古い `try` と新しい exnref) も、Node.js と wasmtime で対応が分かれていて、変換が必要だった。
- Node.js の `node --cpu-prof` で、wasm の関数も名前付きでプロファイルできる。性能の改善に欠かせなかった。

### 5.4 AI と進めた開発について

- 作者が方針 (Lua のランタイムを使う範囲、Go 版と同じ考え方にする点、優先順位) を決め、Claude が設計・実装・テスト・文書化を行った。
  設計の文書 (`wasm_direct_design.md`) を最初に作り、段階 (M0〜M4) ごとに実施内容と課題を追記していく形にしたことで、
  セッションの文脈が途切れても作業を再開しやすかった。
- 「Lua 版と出力が一致する」という機械的に判定できる完了の条件があったので、AI が自律的に進めやすかった。
- 性能や設計の判断 (Lua の呼び出しの扱い、WASI 対応、Lua 版 lnsc の埋め込み) は、作者の指摘で方向が決まった場面が多かった。

### 5.5 マクロの実行 (Lua の VM) について

LuneScript のマクロは、LuneScript の構文をそのまま使えて、コンパイル時の処理 (macro-statement) も LuneScript で書ける。
これを実現するために、どの lnsc もマクロを Lua に変換し、内包した Lua の VM と Lua 版の lnsc で実行している
(wasm 版も、Lua 版 lnsc を埋め込んで同じ方式にした。`wasm_direct_design.md` の 14.11)。
そのため、マクロの展開の速度は Lua のランタイムに依存する。この影響を測った。

`exe` の実行時間 (3 回の値):

| プログラム | wasm 版 lnsc (Node.js) | Go 版 lnsc | Lua 版 lnsc |
|---|---|---|---|
| マクロなし | 0.10〜0.12 秒 | 0.00 秒 | 0.04 秒 |
| コンパイル時の処理を持つマクロを 1 回展開 | 0.10 秒 | 0.01 秒 | 0.03 秒 |
| 同じマクロを 50 回展開 | 0.11 秒 | 0.01 秒 | 0.04 秒 |

- マクロの展開 1 回は、どの lnsc でも 0.2ms 程度で、計測の誤差に埋もれる程度。
  wasm 版で最初のマクロの時に行う、埋め込んだ Lua 版 lnsc の登録もほとんど時間を使わない
  (マクロの実行に必要な Lua のモジュールは一部だけで、Lua 版 lnsc 全体を読み込むわけではない)。
- lnsc の全モジュールの変換でも、マクロの実行を含む Lua の呼び出しは全体の 1.7% (`wasm_benchmark.md` の 2026-10-20 (2))。
- 遅くなるのは、マクロの中で `_lnsLoad` を使い、LuneScript のコードをその場でコンパイルする場合。
  この時は Lua の中で Lua 版 lnsc のフロントエンドが動くので、Lua 版の速度 (Go 版の 10 倍以上遅い) がそのまま効く。

速度よりも、次の利点・欠点の方が大きい。

| | 内容 |
|---|---|
| 利点 | マクロは、Lua 版・Go 版・wasm 版のどの lnsc でも同じ Lua の VM と同じ Lua 版の lnsc で実行されるので、展開結果が必ず同じになる (セルフホストの不動点の前提の 1 つ)。マクロの意味を変換先ごとに実装しなくて良い |
| 欠点 | Lua と Lua 版の lnsc を内包する必要がある (wasm 版では約 2.9MB で、全体の 6 割)。macro-statement から使えるのは標準の関数だけで、マクロの外で定義した関数は呼べない (実行環境が別の Lua の VM のため)。変換先ごとに Lua との橋渡し (Go 版の `depend.go`、wasm 版の `lnslua.c` の glue) が要る |

別の方式との比較:

| 方式 | 内容 | 評価 |
|---|---|---|
| 今の方式 (Lua の VM) | マクロを Lua に変換し、内包した Lua で実行する | 展開結果が全ての lnsc で一致する。通常のマクロなら速度は問題にならない |
| 変換先のコードとして実行 | マクロを Go・wasm に変換して、その場で実行する | Go は実行時にコンパイルできない。wasm は JavaScript のホストなら動的に instantiate できるが、WASI ではできない。変換先ごとに意味がずれる危険もある |
| AST を直接実行するインタプリタ | LuneScript で AST の評価器を書く | Lua も Lua 版 lnsc も不要になるが、実装量が大きく、C で書かれた Lua の VM より遅くなる可能性が高い |

今の方式は、移植性と一貫性のために、速度と処理系の大きさを少し払っている設計と言える。
Lua は「小さく、どこにでも組み込めて、十分速い VM」なので、コンパイル時の評価の仮想マシンとして合理的な選択だと考える。
速度が問題になるのは `_lnsLoad` のような重いマクロに限られるので、方式を変える必要は無い。
改善するなら、`_lnsLoad` の結果のキャッシュなど、重いケースだけを個別に速くする方が効果的である。
